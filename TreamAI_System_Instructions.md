# TreamAI — Full System Design & Development Instructions

## Project Overview

**TreamAI** is an LLM-powered team collaboration assistant built as a Final Year Project (FYP).

The core research contribution is a **self-adaptive memory retrieval system** — not the chat interface itself.

The chat web app is the delivery vehicle. The memory system is the novel contribution.

---

## Tech Stack

```
Backend:     FastAPI (Python)
Database:    SQLite (structured data) + ChromaDB (vector memory)
LLM:         Anthropic Claude API (claude-sonnet-4-6)
Frontend:    React or plain HTML + WebSocket
Hosting:     Oracle Cloud VM (Ubuntu)
```

---

## System Architecture

```
Custom Chat Web App (Frontend)
            ↓ WebSocket
FastAPI Backend
  ├── Storage Pipeline   ← passive message buffering + summarization
  ├── Retrieval Pipeline ← triggered by @agent mention
  ├── SQLite             ← chats, projects, members, weights
  └── ChromaDB           ← memory nodes + embeddings
            ↓
Anthropic Claude API (LLM)
```

## Memory Node Structure

```python
Memory Node {
    id:           uuid,
    content:      "John will finish login module by Friday",
    embedding:    [...],           # auto-generated by ChromaDB
    chat_id:      "chat_123",      # 1st level hierarchy
    project_id:   "proj_A",        # 2nd level hierarchy
    type:         "project_task",  # see Memory Types below
    speaker:      "John",          # for speaker-based filtering
    timestamp:    1234567890,      # for recency scoring
    access_count: 3,               # for frequency scoring
    last_accessed: 1234567999,     # for adaptive pruning
    pool:         "active",        # active or consolidated
    weight_history: {
        retrieved_by: ["semantic", "recency"],
        times_used: 4,
        last_weight_snapshot: { w1: 0.4, w2: 0.35, w3: 0.25 }
    }
}
```

## Memory Types

Used by LLM classifier to tag each memory node.

```
project_task        Tasks assigned to team members
project_decision    Decisions made for a specific project
project_progress    Progress updates on tasks or features
project_issue       Bugs, blockers, problems reported
team_convention     Cross-project team norms and working styles
team_preference     Cross-project team preferences
IGNORE              Greetings, small talk — never stored
```

Type encodes scope implicitly:
- `project_*` → project-level scope
- `team_*` → chat-level scope

Backend splits scope from type at retrieval time.

---

## Memory Hierarchy

```
Chat (root, isolated per chat)
  ├── team_convention nodes   (cross-project)
  ├── team_preference nodes   (cross-project)
  └── Project A
        ├── project_task nodes
        ├── project_decision nodes
        ├── project_progress nodes
        └── project_issue nodes
  └── Project B
        └── ...
```

Each chat is fully isolated — no memory bleeding between chats.

## Storage Pipeline

```
1. User sends message → backend buffers it (in-memory)
2. Backend counts messages per chat
3. Every N messages (tune N experimentally):
      → Backend sends buffered messages to LLM
      → LLM Step 1: classify and group by project using entity matching
      → LLM Step 2: within each project group, split by type
      → LLM Step 3: summarize each group into distinct memory nodes
      → LLM returns structured JSON
4. Backend stores each node into ChromaDB
5. Backend checks for unknown/unassigned messages → asks user at cycle end
6. Backend checks for new project detection → asks user at cycle end

Exception: if @agent is detected → skip to Retrieval Pipeline immediately
```

### LLM Summarization Output Format

```json
{
  "nodes": [
    {
      "type": "project_issue",
      "project_id": "proj_A",
      "content": "Auth bug blocking deployment",
      "speaker": "John"
    },
    {
      "type": "project_task",
      "project_id": "proj_A",
      "content": "John to fix auth bug by tomorrow"
    },
    {
      "type": "team_convention",
      "project_id": null,
      "content": "Team uses Jira for bug tracking"
    }
  ],
  "unknown": ["check the deployment thing"],
  "new_project_detected": false,
  "suggested_project_name": null
}
```

### LLM Classifier Prompt

```
You are a memory classifier for a team collaboration assistant.

Known projects in this chat: {project_registry}

For each message, decide:
1. Is it worth storing? If not, mark IGNORE.
2. Which project does it belong to? Use entity matching against known projects.
3. What type is it? Choose from:
   project_task, project_decision, project_progress, project_issue,
   team_convention, team_preference, or IGNORE

Then group by project and summarize each group.
For each group, produce one node per distinct piece of information.
Merge closely related items into one node.

Return JSON only in the specified format.
```

## Project Detection

### During summarization cycle (passive):

```
Priority 1: Entity matching
  → LLM matches message content against stored memories
  → "auth bug" matches mem_001 in proj_A → assign to proj_A

Priority 2: Unknown
  → Store as unknown, ask user at end of cycle
```

### During @mention (active):

```
Priority 1: Explicit mention
  → User names project directly in message
  → "what's the status of the Auth System?" → proj_A

Priority 2: Entity matching
  → Infer from query content against stored memories

Priority 3: Unknown
  → Bot asks: "Which project is this for? [proj_A] [proj_B]"
```

### Project Registry (stored in SQLite Projects table):

```python
project_registry = [
    {"project_id": "proj_A", "name": "Auth System"},
    {"project_id": "proj_B", "name": "DB Migration"}
]
```

Passed to LLM at every summarization call as context.

### Bot exceptions (passive messages allowed):

```
1. End of every summarization cycle
   → Bot can send one message summarizing what was stored
   → Appends unknown node clarifications if any
   → Appends new project detection if any

2. First message after X hours of inactivity
   → Bot asks: "Still working on [last active project]?"

3. Keyword triggers (backend-level, no LLM needed)
   → Keywords: "new project", "starting on", "switching to"
   → Bot: "Sounds like something new — new project?"
```

## Retrieval Pipeline

```
1. User sends message with @agent
2. Backend detects @agent → triggers retrieval
3. Optional: LLM expands query (implement last, low priority)
4. Backend vectorizes query
5. Multi-path retrieval runs in parallel:

   Semantic path (ChromaDB vector search):
     collection.query(query_texts=[query], n_results=20,
                      where={"project_id": proj_id})

   Recency path (backend metadata sort):
     collection.get(where={"project_id": proj_id,
                            "type": {"$in": inferred_types}})
     sorted by timestamp descending → Top 10

   Frequency path (backend metadata sort):
     collection.get(where={"project_id": proj_id,
                            "type": {"$in": inferred_types}})
     sorted by access_count descending → Top 10

   Chat-level path (team conventions, always included):
     collection.get(where={"chat_id": chat_id,
                            "type": {"$in": ["team_convention",
                                             "team_preference"]}})

6. Merge + deduplicate all candidates
7. Score each node using composite formula
8. Sort by score → Top-K
9. Inject Top-K into LLM prompt
10. LLM generates response + cites USED:[id1, id2]
11. LLM self-evaluates retrieved nodes (second LLM call)
12. Backend updates access_count for used nodes
13. Backend updates weights using EMA
```

## Multi-Factor Retrieval Score

```
retrieval_score = (w1 × semantic_similarity)
                + (w2 × recency_score)
                + (w3 × frequency_score)
```

Where:
- `w1, w2, w3` come from SQLite Weights table
- `recency_score = 1 / (1 + days_since_created)`
- `frequency_score = access_count / max_access_count_in_pool`
- Scores normalized to 0-1 range

Weight sets are determined by node type:
```python
def get_weights(node_type, chat_id, project_id, db):
    if node_type in ["team_convention", "team_preference"]:
        return db.get_weights(chat_id, project_id=None)  # chat-level
    else:
        return db.get_weights(chat_id, project_id)        # project-level
```

## Self-Adaptive Features

### Feature 1 — Adaptive Weights

Weights automatically adjust based on which retrieval paths produced useful results.

#### Step 1 — LLM cites used memory IDs

```
Prompt addition:
"After your response, list the memory IDs you used.
Format: USED:[id1, id2]"
```

#### Step 2 — LLM self-evaluation (second LLM call)

```
Input:  original query + Top-K nodes + generated response
Output: relevance rating per node (1-5)

Prompt:
"Rate each memory node from 1-5 on how useful it was:
  5 = essential, directly used
  4 = helpful, influenced the response
  3 = somewhat relevant
  2 = retrieved but not useful
  1 = completely irrelevant
Return JSON only: { 'mem_001': 5, 'mem_002': 2, ... }"
```

Cost optimization: use smaller/cheaper model for evaluation call, or run every Nth retrieval only.

#### Step 3 — Calculate feedback signal per path

```python
# For each retrieval path:
relevance_score = SUM(ratings) / (n_nodes × 5)
citation_bonus  = 1.0 if node in USED else 0.0
signal = (citation_bonus + relevance_score) / 2
```

#### Step 4 — Update weights using EMA

```python
α = 0.90  # chat-level (stable, slow adaptation)
α = 0.85  # project-level (dynamic, faster adaptation)

w1_new = α × w1_old + (1 - α) × semantic_signal
w2_new = α × w2_old + (1 - α) × recency_signal
w3_new = α × w3_old + (1 - α) × frequency_signal

# Normalize
total  = w1_new + w2_new + w3_new
w1     = w1_new / total
w2     = w2_new / total
w3     = w3_new / total
```

---

### Feature 2 — Adaptive Memory Pruning

Old, unaccessed memories are automatically consolidated or discarded.

#### Pruning Score

```python
prune_score = age_factor × (1 / (access_count + 1))

age_factor = (current_time - timestamp) / max_age
```

High prune_score → candidate for pruning.
Low prune_score → keep.

#### Pruning Outcomes

```
Keep:         prune_score below discard and consolidate threshold
Consolidate:  merge similar nodes → one summary node (LLM call)
Discard:      delete node entirely
```

#### Pruning Config

```python
PRUNING_CONFIG = {
    "discard_threshold_days":     30,
    "consolidate_threshold_days": 14,
    "min_access_count_to_keep":   2,
    "pruning_trigger":            "hybrid",  # daily + count-based
}
```

#### Pruning Trigger

```
Time-based:   runs daily
Count-based:  emergency prune if total nodes > threshold
Hybrid:       both (recommended)
```

#### Linkage to Adaptive Weights

```
Node pruned (discarded):
  → retrieval path that surfaced it was not useful
  → slightly penalize that path's weight

Consolidated node frequently accessed:
  → reinforce pruning aggressiveness for that project
```

## Frontend — Custom Chat Web App

### Why custom (not Google Chat / Telegram):

```
No platform restrictions
Full control over message injection (synthetic evaluation)
Easier to demonstrate system directly
Focuses attention on memory contribution, not platform
```

### Features needed:

```
Chat interface:
  ├── Message input + send button
  ├── Message display (chat history)
  ├── Username selector (simulate multiple users)
  ├── Space/chat selector
  └── @agent trigger support

Agent behavior:
  ├── AI Listening Toggle: Users can toggle if the AI listens in any chat. If off, completely ignored.
  ├── Silent when buffering (no response)
  ├── Responds on @agent mention or leading '?' query
  ├── Shows summarization notification at cycle end
  └── Asks for clarification on unknown projects
```

### Connection:

```
Frontend ↔ FastAPI via WebSocket
  ws://YOUR_ORACLE_IP:8000/ws/{chat_id}/{username}
```

### WebSocket endpoint in main.py:

```python
from fastapi import WebSocket
from bot import handle_message

@app.websocket("/ws/{chat_id}/{username}")
async def websocket_endpoint(websocket: WebSocket,
                              chat_id: str, username: str):
    await websocket.accept()
    while True:
        text = await websocket.receive_text()
        response = await handle_message(chat_id, text, username)
        if response:
            await websocket.send_text(response)
```

## Key Design Decisions

```
1. Vector DB:         ChromaDB (local, free, Python-native)
2. Relational DB:     SQLite (simple, no server needed)
3. LLM:              Claude Sonnet 4.6 (Anthropic API)
4. Memory hierarchy:  Chat-level + Project-level (2 levels)
5. Retrieval paths:   3 paths (semantic, recency, frequency)
6. Weight adaptation: EMA with LLM feedback (citation + self-eval)
7. Pruning:          Hybrid trigger (daily + count-based)
8. Project detection: Entity matching first, explicit mention on @agent
9. Graph structure:   Dropped — metadata + vector DB is sufficient
10. Importance score: Dropped — access_count + memory selection sufficient
11. Type match weight: Dropped — handled as pre-filter, not scoring factor
12. User scope:       Dropped — chat is root, no user-level memory
13. speaker field:    Kept — enables speaker-based metadata filtering
```

## Notes for Development

- LLM never writes to databases directly — backend executes all storage
- LLM never queries ChromaDB directly — backend runs all retrieval
- All retrieval logic lives in backend, LLM only generates text
- Recency and frequency paths use `collection.get()` + backend sort, NOT `collection.query()`
- Semantic path uses `collection.query()` with no type filter
- Type filter only applied on recency and frequency paths
- Weights stored in SQLite, not ChromaDB
- Message buffer is managed in SQLite (Message_Buffer table) to persist across server restarts
- All chat history is saved permanently in SQLite (Messages table)
- Self-evaluation LLM call is optional — run every Nth retrieval to reduce cost
